Web development / Playwright / Lesson 01

Write your first reliable browser test

A browser test should describe what a person can do on a page, then check whether the application behaves as expected. Learn the difference between clicking blindly and testing with confidence.

By the end, you can:✓ Explain the arrange → act → assert workflow✓ Write a basic Playwright test in TypeScript✓ Choose stable, accessible locators

Why test in a real browser?

A unit test can confirm that a function returns the correct result. It cannot, by itself, prove that a user can navigate a real page, enter a value, and see the intended response. End-to-end tests cover that interaction across the browser and the application.

Imagine a sign-in form. The server might accept valid credentials, but the button could be hidden behind another element. A browser test can catch that failure because it interacts with the interface the way a person does.

First checkpointThink of a recent website problem. Was it a calculation problem, a visual interaction problem, or both? Decide whether a browser test would have detected it.

A test has three connected parts

Strong tests have a predictable shape. Prepare the page and conditions, perform a meaningful action, and assert an observable outcome. The final assertion matters: a script that only clicks a button has not proved anything.

Write your first Playwright test

In a Node.js project, install Playwright's test runner using npm init playwright@latest. Choose TypeScript when prompted. Playwright creates configuration and example tests. A minimal test looks like this:

import { test, expect } from '@playwright/test';

test('home page has a clear heading', async ({ page }) => {
  // Arrange
  await page.goto('https://example.com');

  // Act: inspect the user-facing page
  const heading = page.getByRole('heading', {
    name: 'Example Domain'
  });

  // Assert
  await expect(heading).toBeVisible();
});

Save this as tests/home.spec.ts and run npx playwright test. The runner reports whether the expectation passed. The example uses a public demonstration page; use your own local app URL for a real project.

Choose a locator that survives change

A locator tells Playwright which element to interact with. Prefer the role and accessible name a user would recognize. A CSS selector tied to a generated class may break after harmless styling changes.

// Preferred: meaningful to users
await page.getByRole('button', { name: 'Search' }).click();

// Also useful: associated field label
await page.getByLabel('Email address').fill('test@example.com');

// Fragile: dependent on layout and styling
await page.locator('div:nth-child(3) > button.blue').click();

Playwright automatically waits for many interaction conditions, but that does not replace an assertion. Test what matters to the user: a heading, a confirmation message, a changed URL, or an updated result.

Practice: test a course search

Imagine NoteStack's course search. Your test should open the catalogue, enter “Python”, and verify that the Python course appears. Write the expected outcome before writing the interaction steps.

test('finds Python in the course catalogue', async ({ page }) => {
  await page.goto('http://localhost:4173/#/courses');
  await page.getByRole('textbox', {
    name: 'Filter courses'
  }).fill('Python');

  await expect(
    page.getByRole('heading', { name: 'Python Programming' })
  ).toBeVisible();
});

This example assumes your NoteStack project is served at port 4173. Change the URL to match your development server. For an even stronger test, assert that unrelated course cards disappear after filtering.

Takeaway

A reliable browser test describes a user journey and checks its result. Start with accessible locators, a small meaningful action, and one observable assertion. Then expand to error states and edge cases.
