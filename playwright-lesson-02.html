Playwright Testing · Lesson 02

Find the right element and prove the result

A browser test is only as reliable as the element it targets and the outcome it checks. Learn how accessible locators and web-first assertions make tests resilient.

1. Why brittle selectors fail

Imagine a page with two buttons. A test clicks button:nth-child(2). A designer adds a new button above it, and the test clicks the wrong one. Nothing about the user experience broke; the test was coupled to page structure instead of meaning.

Playwright's role-based locators target elements by what they represent to users, such as a button named “Save changes” or a heading named “Your profile”. This is both readable and less sensitive to harmless layout changes.

2. Choose a locator in the right order

For interactive elements, prefer accessible roles and names. For form inputs, labels are often a natural choice. Placeholder text and test IDs can be useful when semantic alternatives are not practical. Avoid selectors that depend on the order of unrelated elements.

// Semantic button
const save = page.getByRole('button', { name: 'Save changes' });

// Label associated with an input
const email = page.getByLabel('Email address');

// Dedicated stable test identifier, when needed
const chart = page.getByTestId('revenue-chart');
Checkpoint

Which is more meaningful: .modal > div:nth-child(4) or getByRole('dialog', { name: 'Delete account' })? Explain why before moving on.

3. Scope locators to avoid ambiguity

If a page contains several “Delete” buttons, identify the relevant row or card first. A locator that matches multiple elements may fail a strictness check. Scoping makes the intended target explicit.

const row = page.getByRole('row', { name: /Quarterly report/ });
await row.getByRole('button', { name: 'Delete' }).click();

The row must have an accessible name containing “Quarterly report” for this example to work. Always inspect your actual page's accessibility structure rather than assuming it.

4. Assertions should wait for meaningful results

After a user clicks Save, the confirmation may appear asynchronously. Playwright's expect API can retry supported assertions while waiting for the condition. Avoid fixed sleeps such as waitForTimeout(3000) when you can assert a meaningful state instead.

import { test, expect } from '@playwright/test';

test('updates a profile name', async ({ page }) => {
  await page.goto('http://localhost:4173/profile');

  await page.getByLabel('Display name').fill('Asha');
  await page.getByRole('button', { name: 'Save changes' }).click();

  await expect(
    page.getByRole('status')
  ).toContainText('Profile updated');
});

This example assumes a sample profile page with the stated labels and status message. Adapt the route and names to your own application. The principle remains the same: test the result, not merely the click.

5. Try a practical challenge

Build a simple page with a labeled search field, a Search button and a result message. Write a test that fills the field, clicks Search, and asserts that the result contains the searched term. Then insert another button above Search. Your test should continue working without changes.

Self-review

Can you identify the locator's accessible name? Does the assertion verify a user-visible outcome? Would the test survive a CSS redesign?

Knowledge check

Key takeaway

Target elements by their accessible purpose, scope ambiguous controls, and verify observable outcomes using Playwright assertions. Tests should describe user behavior, not the incidental structure of the HTML.
